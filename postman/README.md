# Local secretary dependency acceptance

Only **Google Sheets** is simulated. `scripts/acceptance.sh` launches real Rust Core; `scripts/acceptance.ts` calls real exported bridge handlers over HTTP into Core. Core itself is never a simulation member and fetch is never replaced with a stub.

The local custom mock began with `postman mock generate postman/contracts/google-sheets-read.openapi.yaml`, then gained strict query matching and synthetic grid data. The source is the official [spreadsheets.get reference](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/get) and [Sheet/GridData reference](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/sheets), observed 2026-10-25. This is a bounded read subset, not a complete Google contract. Owner-published mock search was skipped; no authenticated owner workspace search, cloud initialization, publication or deployment was performed. Fixtures contain synthetic item labels/amounts and approved schema metadata, never personal workbook contents. Local `require('./fixture.json')` handlers deliberately cannot be deployed unchanged to cloud.

Prerequisites: Postman CLI 1.75+, Bun, Rust dependencies/lockfile available to `cargo run --offline --locked`, free loopback ports 4900 and 8787, no existing Core at 8787. Use only the disposable fixture configuration. Run `bash scripts/acceptance-all.sh` for the fail-fast six-scenario suite, or select an individual case from the repository:

```sh
bash scripts/acceptance.sh read
bash scripts/acceptance.sh writes
bash scripts/acceptance.sh retry
bash scripts/acceptance.sh error
bash scripts/acceptance.sh drift
bash scripts/acceptance.sh slow
bun test scripts/acceptance.test.ts plugins/secretary-tools/test
SECRETARY_HTTP_TESTS=1 bun test plugins/secretary-tools/test
```

The read case checks listing, strict owner and bearer denial, unregistered spreadsheet and unknown view rejection, source evidence, pagination, literal search and wedding report ambiguity. Expected synthetic known cost is 2200; currency, payment balance and completion remain unknown. `retry` serves two 503 responses before succeeding, exercising real Core retries when run. `error` injects persistent 503; `slow` delays beyond the bridge's five second budget; `drift` changes a required header and expects safe rejection. Each simulation has exactly one Google member. All unsupported routes return 501. No mock scheduler, Core, WhatsApp or memory service is introduced. Stateful write workflow is provided below; all six scenarios passed in the qualified local Linux runtime (T017).

The native RPC adapter fixture checks execution/completion independently of delivery evidence through the public reminder history tool. It is not live Gateway, restart persistence or WhatsApp proof. The HTTP tests remain actual loopback stand-ins. All four passed with the pinned Bun 1.2.21 in the qualified Linux runtime (T017). Native sandbox bind remains prohibited; these standalone checks do not execute Rust Core or the Google-only simulations.

Observed 2026-10-26: all six scenarios passed with Postman CLI 1.75.0, Node 24.22.1, Bun 1.2.21 and actual Rust Core. Google member traffic was inspected for read, writes, retry and drift. Injected error/latency conditions intercept before member request logging; actual caller error/deadline assertions passed. Keep `TMPDIR=/tmp` inside the container: Postman dataset support failed when scratch used the host-mounted log directory. `SECRETARY_ACCEPTANCE_LOG_ROOT=/runs` separately persists private run logs. See [local verification](../docs/local-verification.md) and the adjacent scenario context notes. No raw request logs are committed.

Stateful write extension (2026-10-26): `bash scripts/acceptance.sh writes` uses `registry-writes.json`, existing synthetic AI_Tasks/AI_Payments tables and async `pm.state` keys prefixed `google-sheets-writes:`. Official [values.append](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/append) and [values.batchUpdate](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/batchUpdate) ground the modeled endpoints. Append preserves numeric types and returns updated range/evidence; batch updates requested owned cells; later GET returns stored data. This is bounded table behavior, not a full Google emulator.

The real public workflow tests preview, separate operator approval, append/update, wrong owner/business bearer, unapproved and forged-approved inputs, changed payload/digest, replay without duplicate rows, intervening external edit conflict, history, and loss of the provider response after state is saved. Core must mark uncertainty, reject blind replay, then reconcile by observation to exactly one payment. Local controls reset state and arm one response loss; these are not Google endpoints. The approval-qualified flag is enabled only in this disposable harness to exercise Core; it does not qualify actual approval transport. The stateful HTTP scenario passed, including accepted-write/lost-response reconciliation to one payment. Payment fixture setup reads an actual synthetic cost-group reference through Core instead of inventing one. Live Google authentication and host approval transport remain separate gates.

The write scenario now builds the actual plugin entry and also runs `scripts/acceptance-entry.ts` through registered tool factories and the registered approval hook (T019). The actual installed SDK and distribution bundle execute; only the host registration surface is a boundary fixture. This checks lazy credential/runtime access, preview sharing within one API, isolation across APIs, owner/revocation guards and one-shot approval followed by a single synthetic append. It does not qualify actual host approval UI, Gateway policy execution or requester provenance. Run writes with the qualified SDK environment; the launcher rebuilds before starting the simulation.

T021 verified all six cases sequentially in one network-isolated container. Core is compiled before readiness polling and its actual emitted executable runs directly. Cleanup signals only the simulation's dedicated process group, allows a bounded shutdown grace period, then reaps owned processes before the next case. This handles Postman's npm wrapper/CLI/dataset children and avoids leftover listeners. Python3 is required for process-session isolation. SIGINT/SIGTERM exit with their conventional nonzero status and use the same cleanup.

The full CI job now runs this suite after `scripts/verify.sh`, with pinned Postman1.75.0, no lifecycle scripts, no login/API key or live target, and no raw-log upload. Workflow permissions remain read-only. This is configured and locally exercised, not an observed hosted CI pass.
