# T022 — Keep lightweight architecture and fix journal lock handoff

Date: 2026-10-27. Status: decision recorded and local verification passed. Owner decision: retain FSM + one in-process command bus after discussing CQRS. Full verification exposed an intermittent journal ownership defect; diagnosis and final checks are recorded below.

## Architecture decision

[ADR0001](../../docs/adr/0001-lightweight-command-bus-and-operation-fsm.md) records the deliberate trade-off against separate buses/read stores, brokers, projection workers and event sourcing. The architecture guide/source comments clarify that `Command` includes typed reads and mutations and `MutationCommand::History` is operation-history access. No enum, handler, public route or API contract changed. Sheets remains authoritative for planning, OpenClaw owns personal memory/native reminders and Core keeps the durable operation FSM/journal.

## Reproduced failure and diagnosis

The first full verification attempt failed at immediate journal reopen in the restart test. A loop of the original five journal tests failed on attempt 4; another instrumented run failed on attempt 8. The isolated restart and two-test restart/backup subset each passed 30 runs, so a single green retry would not establish a fix. A 200-open/drop probe without the competing suite also passed.

Temporary staging-only diagnostics located the failure at `lock.try_lock()`, before SQLite connection/recovery. Candidate causes were asynchronous SQLite close, transient inherited lock descriptors during subprocess creation, and general test concurrency. The lock acquisition trace ruled out SQLite initialization as the immediate failure.

A deterministic regression duplicates the actual Journal lock descriptor (same open-file-description retention as inheritance), drops the Journal, keeps the duplicate alive, and immediately reopens. It failed against the original implementation because the duplicate prolonged the old file lock after the application owner ended. A second regression verifies a genuinely live Journal clone still excludes another owner. This locks down ownership semantics without sleeps, broad retries, serialized tests or a subprocess-specific dependency.

## Fix and checks

A small shared RAII guard now explicitly unlocks the file when its last application-owned handle drops. The guard is installed immediately after successful lock acquisition, covering startup failure paths too. Journal clones share the guard, so dropping one clone cannot release another live clone's ownership. Closing inherited descriptors remains ordinary OS cleanup; they no longer determine the application's lock lifetime. FSM transitions, approvals, atomic journal updates and fail-closed second-owner behavior remain intact.

The deterministic regressions pass. The original five-test parallel suite passed 50 iterations after the fix, versus the recorded failures before it. Temporary diagnostics and the open/drop probe were removed; no debug logging, arbitrary startup retry, sleep or worker was added to production code.
